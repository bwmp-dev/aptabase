# MultiShock GlitchTip retirement acceptance

**Decision: do not retire GlitchTip yet.** The collector and dashboard support the tested Windows managed-error path under one Aptabase login. The remaining gates are application runtime, actual-app envelope inventory, and production cutover/restore evidence. Android ELF support does not establish MultiShock compatibility.

This is the current acceptance matrix; older checkpoint totals in `monitoring-roadmap.md` are historical. No MultiShock source/configuration, live GlitchTip service or private issue content was changed or copied. No production DSN is stored here.

## Cutover and history preservation plan (not executed)

1. **Keep current GlitchTip and MultiShock unchanged while gates are open.** Record which existing features the owner actually relies on (including any notifications, sessions, attachments or historical search); unknown usage is not permission to discard it. Local Aptabase alerts do not replace an external notification channel if one is required.
2. **Preserve history before redirecting or deleting anything.** With separate owner authorization, inventory the deployed GlitchTip version, PostgreSQL schema/database and any artifact/object storage. Take a consistent database backup and matching artifacts/configuration needed to restore that exact version. Store credentials separately in the owner's secret store, encrypt backup media and restrict access; don't export private events into this repo or synthetic fixtures.
3. **Prove restoration in isolation.** Record backup timestamps and SHA256 manifests, restore to a non-public environment with outbound delivery disabled, and compare per-project issue/event counts, selected old links, timestamps, status and attachments where used. Define the acceptable retention window and recovery time with the owner. A successful backup command alone is not a restore test. No generic importer is offered: preserve the old data format and restore capability until a separately scoped migration is validated.
4. **Authorize a real application candidate.** Obtain the exact missing app dependencies through the owner's normal build process; preserve the existing app and credentials. Test a separately identified published candidate against a disposable collector with matching Portable PDBs, original consent semantics and isolated startup/device services. Inventory all emitted item types. Explicitly agree any lost Sentry functionality before changing unsupported options. Reduced harness results cannot certify this full candidate.
5. **Rehearse the actual hosting boundary.** Use the intended HTTPS reverse proxy, Aptabase session/magic-link settings, private database and persistent storage. Verify owner/shared-reader/revocation, supported error and performance delivery, failure/status logs, database outage/recovery without false acknowledgment, disk/retention bounds and restore. Pin runtime/container/worker versions and patch them; the package patch below does not update the installed .NET runtime or deployed images. Do not use the disposable MonitoringHost in production.
6. **Cut over only after the owner accepts evidence.** Record app version/release/channel, candidate collector version and a short observation/rollback window. Keep the old app configuration/DSN in a secure rollback location, never this repo. Avoid duplicate capture pipelines. Compare synthetic canaries and expected event traffic/rejections while preserving privacy and consent. If supported events disappear or diagnostic fields regress, restore the prior configuration through the normal release process; do not delete newly collected data.
7. **Retire the service separately from deleting history.** Once runtime/operation/restore gates pass, stop new ingestion to GlitchTip under explicit approval. Keep the encrypted, verified historical archive and restoration instructions for the agreed period. Only remove the running instance after the owner accepts how old data/links will be accessed; retain rollback artifacts. No current step authorizes deletion, deployment or changes to live services.
