# One-login Windows monitoring: evidence and migration gates

The target is one Aptabase login for analytics, errors and app performance. This is an integrated collector/dashboard, not a second identity service or an iframe around GlitchTip. Local MultiShock candidate source/disclosure changes are now implemented; live GlitchTip and deployed app configuration remain untouched. A future replacement needs the application-specific gates below; the synthetic SDK probes are not approval to switch production traffic.

**Current retirement decision and evidence:** [MultiShock acceptance matrix](glitchtip-retirement-readiness.md). The preflight/preparation sections below retain historical no-launch findings; later user-operated reduced-harness handled and automatic WinUI deliveries supersede them only for those captured events. Exit/watchdog completion, process-restart replay and actual MultiShock acceptance remain open.

## Shared authentication and permissions

All dashboard routes live under the existing `AuthProvider`, `AppsProvider` and `ConsoleLayout` in `src/webapp/router.tsx`. The same Application navigation includes Dashboard, Errors, Performance, Releases and owner-only Settings. Monitoring settings, DSNs and native artifacts are inside Settings; alerts and issue diagnostics are inside Errors. There is no separate monitoring login, user table or organization membership.

Production uses the existing `auth-session` cookie and `IsAuthenticated` filter. Monitoring reads use the current Aptabase identity and existing app owner / `app_shares` membership. Owners can resolve/reopen, manage capture/retention/alerts, provision DSNs and upload/delete symbols. Shared readers can read issues, performance, releases and resolved frames, but cannot manage them. An App-Key or Sentry ingestion DSN does not grant dashboard access. Monitoring additionally denies deleted apps and locked owners. Existing analytics authorization is preserved.

`AppAccessTests.Existing_Aptabase_Login_Covers_Analytics_And_Monitoring_With_Shared_App_Permissions` exercises the production application and its real registration/magic-link cookie flow, using only a disposable local mail catcher. One authenticated client reads analytics/raw errors/issues/transactions/performance/releases/settings/alerts/DSNs/symbol metadata. Another account is denied, then gets read-only access through an app share, and loses access when the share is removed. An anonymous client carrying the app ingestion key remains unauthorized. This complements the headless monitoring host, whose test login and app-list endpoints are synthetic and do not test production login delivery.
