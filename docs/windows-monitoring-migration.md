# One-login Windows monitoring: evidence and migration gates

The target is one Aptabase login for analytics, errors and app performance. This is an integrated collector/dashboard, not a second identity service or an iframe around GlitchTip. No existing GlitchTip data or MultiShock/Luma configuration was changed during this work. A future replacement needs the application-specific gates below; the synthetic SDK probes are not approval to switch production traffic.

## Shared authentication and permissions

All dashboard routes live under the existing `AuthProvider`, `AppsProvider` and `ConsoleLayout` in `src/webapp/router.tsx`. The same Application navigation includes Dashboard, Errors, Performance, Releases and owner-only Settings. Monitoring settings, DSNs and native artifacts are inside Settings; alerts and issue diagnostics are inside Errors. There is no separate monitoring login, user table or organization membership.

Production uses the existing `auth-session` cookie and `IsAuthenticated` filter. Monitoring reads use the current Aptabase identity and existing app owner / `app_shares` membership. Owners can resolve/reopen, manage capture/retention/alerts, provision DSNs and upload/delete symbols. Shared readers can read issues, performance, releases and resolved frames, but cannot manage them. An App-Key or Sentry ingestion DSN does not grant dashboard access. Monitoring additionally denies deleted apps and locked owners. Existing analytics authorization is preserved.

`AppAccessTests.Existing_Aptabase_Login_Covers_Analytics_And_Monitoring_With_Shared_App_Permissions` exercises the production application and its real registration/magic-link cookie flow, using only a disposable local mail catcher. One authenticated client reads analytics/raw errors/issues/transactions/performance/releases/settings/alerts/DSNs/symbol metadata. Another account is denied, then gets read-only access through an app share, and loses access when the share is removed. An anonymous client carrying the app ingestion key remains unauthorized. This complements the headless monitoring host, whose test login and app-list endpoints are synthetic and do not test production login delivery.

## Safe migration plan (not executed)

1. **Prepare an isolated Aptabase test app.** Keep the existing GlitchTip service and current MultiShock release unchanged. Configure retention/capture deliberately; local alerts remain off unless enabled. A single Aptabase account owns the app and grants read-only shares as needed. Obtain its release/debug DSNs from Settings → Monitoring; never put dashboard cookies into a client.
2. **Test an explicitly authorized MultiShock build separately.** Pin Sentry.Maui6.8.0 initially. Change only that test build's DSN and supported-subset settings. Preserve release/environment and PII-off policy, disable sessions/client reports/attachments/profiling/unsupported automatic integrations, and keep matching Portable PDBs with the published assemblies. Apply source-path/snippet/free-text scrubbing before capture. Avoid duplicate crash reporting through both Aptabase and Sentry.
3. **Verify the actual published Windows build.** Capture a synthetic handled error at a known method/basename/line/column and compare collector storage and UI. Verify WinUI/UI-thread and background unhandled errors, flush/termination behavior, exact supported envelope types, gzip/size rejection, release/debug isolation, manual app transaction/spans, and offline/restart retry behavior. Do not infer these from core-SDK serialization or a MAUI library build. Confirm sharing, revocation, logout and analytics still work under one real login behind the intended HTTPS reverse proxy.
4. **Review losses explicitly.** This subset drops users/breadcrumbs/tags/arbitrary context/source snippets and retains only the final exception in a chain. It rejects envelopes containing unsupported extra items as a whole. Sessions/release-health, full Sentry management APIs, native dumps, profiling/replay, server PDB/dSYM/source-map uploads, external alert channels and imported GlitchTip history are not implemented. Decide whether these are required for MultiShock before replacement; do not silently discard them as parity.
5. **Cut over only after owner acceptance.** Keep the old DSN/configuration available for rollback and preserve old history under its existing retention. There is no implemented history migration; switching a client does not import GlitchTip issues. Test new releases against Aptabase first. Decommissioning the old instance, changing production settings or enabling external delivery needs a separate explicit action; none was performed here.

## Remaining blockers for a one-login MultiShock replacement

- A real authorized MultiShock/WinUI packaged-build run with Sentry.Maui6.8.0, exact current integrations and actual published PDBs; this is the principal compatibility gate.
- Application-level restart/offline crash durability, sampling, payload bounds, unsupported-item handling and privacy review. The sample runners are diagnostic fixtures, not production queues.
- Production HTTPS/auth/session and worker topology, resource/load/backup/retention validation; existing NuGet PKCS advisories still need a separately scoped dependency assessment.
- An owner decision on required historical GlitchTip data and unsupported features before decommissioning. No binary symbol pipeline is required for the already-working managed Portable-PDB client frames.

Android ELF source resolution is a separate optional capability and does not cover MultiShock or Windows Rust/Luma binaries. Luma can use sanitized panic file/line diagnostics without a native address-symbolication service; production panic queuing, Tauri hooks and abort/native failures still need app-specific work. Apple/device work is not on the critical path to this Windows one-login goal.


## Actual MultiShock preflight: launch blocked before execution

Owner authorized actual published-app tests using an isolated copy, preserving the current app and GlitchTip. Read-only inspection of `D:/Coding/PiShock/MultiShock/MultiShock` at source commit `a27d356d38f5a403486ea71f69c690df53510cea` found these concrete boundaries:

- `Core/MauiProgram.cs:74` constructs the normal configuration before SDK setup. `MultiShock.Core/Configuration/AppPaths.cs:28` resolves Windows LocalApplicationData and creates PiShock/MultiShock directories. Configuration can migrate/back up/write files; plugins, logs, flows and MAUI Preferences have additional persistence paths. A copied executable or changed working directory does not isolate these paths. The configuration constructor alone accepts a test filename but startup does not supply it and it does not redirect all other storage.
- `Core/MauiProgram.cs:219-241` records startup, constructs the serial relay and starts plugins, device initialization, WebSocket channels and flows. Device initialization verifies login, connects services and starts serial detection when credentials succeed. The relay can forward operate commands to USB devices. No device was queried or controlled during this inspection.
- Startup also fetches the plugin catalog and checks app updates (`MauiProgram.cs:264,278`). `Platforms/Windows/App.xaml.cs:20` runs Velopack before MAUI setup. The project supplies production telemetry defaults at build time; the release script omits empty override arguments. Merely setting an empty environment variable is not a verified way to disable baked-in endpoints.
- `Core/App.xaml.cs:20-22` creates a normal MAUI window/MainPage. Repository-wide source search found StartMinimized only in its settings model and tests, not in a runtime window path. No verified headless launch switch exists. Hiding a process at launch does not establish that MAUI will not activate a later window or show crash UI.
- Source pins Sentry.Maui6.8.0, but existing `bin/Publish/win-x64-sdk1.15.0-rt10.0.12` executable/DLL/PDB timestamps predate this source checkout. Their runtime identity and PDB matching were not established. Do not treat this old publish directory as current6.8.0 acceptance.
- No running process named MultiShock was found at inspection time. No process was ended. No original files/configuration, registry, permissions, device state or external service were changed. No published executable or app assembly was loaded/executed.

Minimum safe next execution must use a fresh disposable source copy, not the old published binary. In that copy only: replace the early startup with an explicit test branch that disables Velopack, analytics, plugin discovery/initialization, device/serial/relay/WebSocket/flow services, update/catalog checks and normal MainPage/WebView startup; redirect every app/SDK/cache/preference/log path to scratch; give it a distinct identity; use a fixed loopback-only SDK transport with redirects/proxies refused; preserve real UseSentry integration and record emitted envelope types. Do not copy the personal configuration/plugins/flows. Audit the resulting publish before running, and enforce a bounded watchdog with no error dialog. Modified-copy evidence must be labelled separately from unchanged published-app acceptance.

**Pending technical blocker, not an access denial:** there is no verified non-disruptive WinUI execution environment/path for exercising the actual UI-thread crash hook without activating a window and potentially using platform profile storage. A dedicated disposable Windows session/VM with no devices, personal profile or live network access, or an explicitly scheduled visible test, is needed before this runtime gate can proceed. Creating/launching such an environment or changing permissions was not attempted. Skipping window creation would test another partial harness, not the requested actual WinUI hooks. No runtime test was run: handled/unhandled/shutdown/offline delivery and configured envelope-type compatibility remain open for MultiShock.
